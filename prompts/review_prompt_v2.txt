ASSERTION TYPES
==============================================================================

Use exactly one assertion per finding.  Choose the type that best matches:

1. method_is_not_async
   Use when: you believe a method is NOT declared with the `async` keyword.
   Fields:  target_class (str), method (str), file_hint (str, optional res:// path)
   Example: {"type": "method_is_not_async", "target_class": "Gun", "method": "fire"}

2. node_type_mismatch
   Use when: the code accesses a node via $Path but the scene has a different type.
   Fields:  node_path (str, e.g. "$CollisionShape3D"),
            expected_type (str, what the code treats it as),
            actual_type (str, what you believe the scene actually has),
            scene_file (str, res:// path to the .tscn)
   Example: {"type": "node_type_mismatch", "node_path": "$CollisionShape3D",
             "expected_type": "CollisionShape3D", "actual_type": "CollisionShape2D",
             "scene_file": "res://ships/enemies/pirate/pirate_ship.tscn"}

3. identifier_not_defined
   Use when: an identifier (class_name, autoload, constant) appears undefined.
   Fields:  identifier (str), suggested_match (str, optional), search_scope (str, optional)
   Example: {"type": "identifier_not_defined", "identifier": "Projectile",
             "suggested_match": ""}

4. signal_not_declared
   Use when: a signal is emitted/connected but never declared in the script
             (or its ancestors).
   Fields:  signal_name (str), file (str, res:// path)

5. node_not_found
   Use when: the code accesses a node path that does not exist in the scene.
   Fields:  node_path (str), scene_file (str, res:// path)

6. file_not_exists
   Use when: a preload/load/reference points to a file that does not exist.
   Fields:  path (str, res:// path)

7. unverifiable
   Use when: your finding is valid but does NOT match any of types 1–6.
   Fields:  (none required beyond "type")
   IMPORTANT: "unverifiable" findings MUST use severity "warning" or "info", NEVER "error".
   Only verifiable assertions (types 1–6) can support severity "error".

RULE: If your finding does not fit types 1–6, you MUST use type "unverifiable".
NEVER use a real assertion type with fake/placeholder parameters (e.g. signal_name:

==============================================================================
SEVERITY RULES
==============================================================================

"error" — code that WILL fail when the execution path is reached:

- Accessing a property that does not exist on the node type
  (e.g. $CollisionShape2D.polygon — CollisionShape2D has no polygon property)
- Calling a method on a null/freed object without a null check
- Accessing @onready variables before _ready() has run
- Connecting signals without is_connected() guard when the connection can happen
  multiple times
- Array/Dictionary access without key existence check when the key is not
  guaranteed

"error" does NOT require the path to be triggered in normal gameplay.
If the code path EXISTS and WILL crash when reached, it is an error.
The game running successfully only means the path hasn't been reached YET —
it does not downgrade the severity.

"warning" — code that MAY cause issues under specific conditions:

- Resource/node not freed (memory leak, not a crash)
- Missing type hints (style, not a bug)
- Redundant await that works but adds noise
- Performance concerns (per-frame allocations)
- Signal patterns that could leak but have mitigating factors

"info" — pure style or documentation suggestions

KEY DISTINCTION: "will crash WHEN reached" = error.
"might cause problems IF conditions align" = warning.
Do NOT consider whether the path is reached in normal gameplay.
